# 1.0.8 elongated subtype 및 elongated_linearity dead code 제거

---

## (사용할 skills: feature-dev)

## 개요

Severstal 강판 결함 탐지 데이터셋에서 `elongated` subtype 발생 건수가 0이다. `defect_characterization.py`의 분류 조건(`aspect_ratio > high_aspect_ratio AND linearity > elongated_linearity`)을 만족하는 결함이 실 데이터에 존재하지 않으므로, 관련 분기·임계값·템플릿·프롬프트·배경 호환성 가중치가 파이프라인 전 구간에 걸쳐 dead code로 잔존하고 있다. 이를 일괄 제거하여 코드베이스를 데이터 실측 기반으로 정렬한다.

---

## 영향도 분석

### 이 기능이 변경하는 상태
- `SUBTYPES` 목록: `"elongated"` 항목 제거
- `defect_characterization.py` 분류 로직: `elongated` 분기 소멸 → 해당 조건 결함이 `general`(또는 `linear`)로 fallthrough
- `elongated_linearity` threshold 파라미터: config 시스템 전체에서 제거
- `COMPATIBILITY_MATRIX` / 배경 호환성 가중치: `elongated_region` 항목 제거
- `recommended_config.yaml` 자동 생성 산출물: `elongated_linearity` 키 미생성

### 그 상태를 전제로 동작하는 기존 로직
- `config_loader.py`의 threshold 검증: `elongated_linearity` 항목 제거 후 기존 YAML에 해당 키가 잔존해도 오류 없이 무시되어야 함
- `roi_extraction.py:404`의 threshold dict 구성: `elongated_linearity` 참조 제거

## 수정 내용

### 1. `src/analysis/defect_characterization.py` — elongated 분류 분기 + 임계값 제거

elongated 분류 조건 분기 제거:
```python
# 제거 대상
elif aspect_ratio > self.high_aspect_ratio and linearity > self.elongated_linearity:
    return 'elongated'
```

생성자 기본값 및 인스턴스 변수 제거 (L29, L46):
```python
# 제거 대상
'elongated_linearity':  0.6,
...
self.elongated_linearity = float(t.get('elongated_linearity', d['elongated_linearity']))
```

**주의**: 분기 제거 후 분류 순서 확인 필요. aspect_ratio가 높지만 linearity가 낮은 결함은 기존에 elongated가 아닌 다른 조건으로 분류됐을 것이므로 영향 없을 가능성이 높으나, fallthrough 경로가 `general`인지 명시적으로 검증한다.

### 2. `scripts/analyze_dataset.py` — SUBTYPES + threshold 항목 제거 (L89, L99, L896, L974)

- `SUBTYPES` 리스트에서 `"elongated"` 제거
- thresholds dict에서 `"elongated_linearity": 0.6` 제거
- threshold recommendation 튜플에서 `elongated_linearity` 항목 제거 (L896)
- 요약 출력 라인에서 `"elongated_linearity"` 제거 (L974)

### 3. `src/utils/config_loader.py` — elongated_linearity 검증·매핑 제거 (L29, L111)

유효성 검사 범위 dict 및 threshold key 매핑에서 제거.

기존 `recommended_config.yaml`에 `elongated_linearity` 키가 잔존할 경우: `config_loader`의 unknown-key 처리 정책을 확인하여 silent ignore가 보장되는지 점검한다. strict reject 방식이라면 하위호환 처리(warning 로그 후 무시) 추가.
